## P1 — новая регрессия правила Throw

### 1. Бросок захваченной цели снова наносит не BODY, а урон безоружной атаки

**Где:** `src/components/WeaponsSection.tsx:237-238`; тест `tests/audit-fixes.test.cjs:258-279`.

Сейчас:

```ts
const handleRollThrow = () => {
  onRollCustomDamage?.(
    `... (${unarmedDamage}) ...`,
    unarmedDamage
  );
};
```

По правилам Cyberpunk RED бросок захваченной цели (Throw) наносит **урон, равный BODY атакующего, напрямую по HP**, игнорируя броню и не снижая SP (`corebook`, стр. 177–179). Предыдущая версия как раз использовала `String(body)`; в рамках исправления текст подписи был приведён к «unarmed damage», но само правило изменено неверно.

Хуже того, новый тест `audit: WeaponsSection throw ...` явно ожидает `3d6` для BODY 8 и тем самым закрепляет ошибку. Тест нужно исправить вместе с кодом.

**Исправление:** вернуть `String(body)` и текст «BODY напрямую по HP»; обновить тест на `'8'` при BODY 8.

## P1 — потеря данных и восстановление

### 2. Баннер восстановления удалён, а новая строгая валидация может незаметно заменить старую коллекцию

**Где:** `src/App.tsx:449`; `src/utils/storage.ts:15-29`, `:82-126`; `src/utils/characterValidation.ts:97-106`.

Коммит `ee36995` удалил с основной страницы баннер восстановления и кнопки:

- «Выгрузить резервную копию»;
- «Восстановить прошлую коллекцию».

Теперь `hasStorageRecovery` и `restorePreviousCharacters` фактически не используются в рабочем UI: `exportStorageRecovery` вызывается только из ErrorBoundary. При этом `saveCharactersToStorage` по-прежнему создаёт резервные копии.

Одновременно `isCharacter` стал строже. Например, теперь он отклоняет отрицательный `cashEb` (`characterValidation.ts:104`), а раньше отрицательное значение можно было ввести в поле денег (`GearSection.tsx:189-191`) и сохранить. Если такая коллекция уже лежит в LocalStorage:

1. `loadStoredCharacters` получает `isCharacterCollection(parsed) === false`;
2. возвращает двух демонстрационных персонажей (`storage.ts:114-126`);
3. `App` сохраняет их поверх;
4. повреждённый/старый оригинал уходит в recovery, но **никакого уведомления и кнопки восстановления в UI больше нет**;
5. `restorePreviousCharacters` тоже проверяет старую коллекцию новым `isCharacterCollection` и может вернуть `null`.

Это регрессия для пользователей старых сохранений. Нужно либо мигрировать/нормализовать данные перед проверкой (например, ограничивать отрицательные значения), либо вернуть доступный recovery-баннер/пункт меню, не показывая его постоянно.

**Дополнительно:** `restorePreviousCharacters` не вызывается из `App`; соответствующий тест проверяет только функцию и создаёт ложное впечатление, что UI восстановления существует.

### 3. Debounce заметок может записать заметки старого персонажа в нового

**Где:** `src/components/NotesSection.tsx:51-104`; `src/App.tsx:163-165`.

В `NotesSection` появился debounce на 400 мс:

```ts
pendingNotesRef.current = md;
debounceTimerRef.current = setTimeout(() => {
  onUpdateCharacter({ ...characterRef.current, notes: md });
  pendingNotesRef.current = null;
}, 400);
```

Проблемы:

- `characterRef.current` содержит **текущего** персонажа на момент срабатывания таймера, а не того, для кого были введены заметки;
- cleanup-эффект зависит от `[onUpdateCharacter]`. В `App` `handleUpdateActiveCharacter` создаётся заново на каждом рендере, поэтому cleanup выполняется практически при каждом обновлении App, а не только при unmount;
- если пользователь редактирует заметки персонажа A и быстро переключается на B, cleanup/таймер может вызвать `onUpdateCharacter({ ...B, notes: notesA })`;
- последние 400 мс также теряются, если вкладку закрыть без React-unmount (cleanup на `beforeunload` не зарегистрирован).

Это уже не только производительность, а риск порчи заметок другого персонажа. Нужно хранить `characterId` вместе с pending-заметкой, очищать/сбрасывать pending при смене ID и использовать стабильный callback (или ref на callback), а также сохранять на `pagehide`/`beforeunload`.

## P2 — новые особенности гранат

### 4. Стекирование гранат создаёт «фантомную» ёмкость

**Где:** `src/utils/backpack.ts:24-49`, `:78-86`, `:122-146`.

`consolidateGrenadeWeapons` использует `magCapacity` как общий размер стека. Если в данных есть полностью израсходованный стек `currentAmmo: 0, magCapacity: 5`, то при слиянии с живым стеком `1/1` получается `1/6`:

- текущих гранат остаётся 1;
- отображаемая ёмкость увеличивается на 5;
- пользователь видит `1 / 6`, хотя пять гранат уже израсходованы.

Проверено отдельным вызовом `consolidateGrenadeWeapons`: результат `{ currentAmmo: 1, magCapacity: 6 }`.

Нужно либо удалять пустые стеки, либо не увеличивать capacity на `addedCap` при `addedAmmo === 0`.

### 5. Ручное добавление гранаты может добавить сразу 8 штук

**Где:** `src/components/WeaponsSection.tsx:151-178`.

`handleAddWeapon` для не-Melee оружия берёт `newWeapon.currentAmmo` (по умолчанию 8) и передаёт его как `weapon.currentAmmo`. Если пользователь меняет категорию на `Thrown Grenade`, но не меняет `currentAmmo`, ветка стекирования добавляет 8 гранат:

```ts
const addedAmmo = weapon.currentAmmo || weapon.magCapacity || 1;
```

Для одиночной гранаты логичнее всегда `1`, либо требовать явное количество.

### 6. Неизвестная граната из рюкзака получает 6d6 обычного урона

**Где:** `src/components/GearSection.tsx:101-136`, особенно `:127`.

Если предмет распознан как граната по названию/категории, но не найден в `GRENADE_CATALOG`, создаётся fallback-оружие с `damage: '6d6'`.

Для дымовой, светошумовой, слезоточивой или иной условной гранаты это неверно: у неё может не быть обычного взрывного урона. Нужно либо не создавать fallback с боевым уроном, либо оставлять `damage: ''` и требовать ручного описания эффекта.

Но повторное ревью не позволяет назвать ревизию `ee36995` полностью безопасной:
